# UI 验收与只读评审

## 实际页面检查

在有可运行项目时，优先检查真实页面而不是只读代码。先在主要视口操作到主要结果，再按产品支持范围检查另一代表视口的阅读与主操作。加一个最可能暴露本次风险的状态，例如最长内容、空态、错误恢复或本次改动涉及的状态。局部改动检查改动处及相邻内容；没有实际风险时不扩成页面 × 设备 × 状态矩阵。

### 视觉

- 一眼能找到页面主题、首要内容和主操作。
- 标题/正文/辅助信息的字号、字重、行距和长度有清楚层级。
- 容器宽度、边距、列间距和纵向节奏一致；首屏没有意外空洞或内容挤压。
- 颜色比例符合方向；文字与背景对比清楚；强调色不会处处出现。
- 图像比例、裁切、清晰度和来源适合内容；图标风格一致。
- 卡片、线条、阴影、渐变、徽标和背景效果均有具体用途。
- 窄屏没有横向溢出、不可触及操作、遮挡文字或异常折行。

### 交互与状态

- 按钮、链接、输入、菜单、弹窗有正确语义和明显的键盘焦点。
- hover、focus、pressed、disabled 状态有可辨反馈；触屏不依赖 hover。
- 表单、加载、空态、错误、成功和禁用状态与本页面相关的均被覆盖。
- 动效不会阻止内容可见或操作；减少动态效果偏好下提供恰当静态体验。
- 刷新、返回、提交与关闭操作不会造成重复或丢失已确认的状态（若业务适用）。
- 若本次涉及保存型界面，保存后刷新并读回，再检查一个失败或恢复路径；不把无关接口问题伪装成视觉缺陷。

## 只读评审格式

按严重程度列出发现，每条包含：

1. **位置/证据：** 页面、视口或具体控件，以及截图或可观察现象。
2. **问题与影响：** 用户会看不见什么、误操作什么或多花什么成本。
3. **建议：** 一条具体可执行的改法。

先报告影响完成任务或阅读的阻塞问题，再报告一致性和细节问题。没有实际运行页面时将代码推断标成推断；不虚构截图结果或无障碍通过结论。

## 交付前减法检查

- 有没有装饰元素能删而不损失理解？
- 是否有两种以上视觉效果在争夺同一焦点？
- 是否出现没有数据或产品依据的数字、评价、徽章或承诺？
- 是否通过新增样式绕过了已有共享 token 或组件？
- 失败、空内容和减少动效时，页面是否仍然完整可用？
