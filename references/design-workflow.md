# Pika UI 设计流程

按任务走必要的部分。小改动不需要重新定方向；已经确认的方向不应每轮推倒重来。

## 1. 建立任务地图与六项方向卡

从用户请求和相关页面明确：

- 页面面向谁、他们要完成什么。
- 首屏最重要的信息、主要操作和次要操作。
- 页面类型：说服/品牌表达、浏览与选择、操作型工作区、内容阅读或单一组件。
- 用户给定的品牌、文案、参考图、目标设备和交付形式。
- 目标平台、项目里的页面/视图、共享组件、设计 token、已有 UI 库和运行方式。

不要先问一串问题。仅当一个未知项会造成不同页面结构或不同产品方向时再问；其他项从项目和上下文推断。

开始实现前，在回复或设计说明里写出六项具体决定。可以很短，不需要另建文档；写不具体的地方就是尚未解决的设计问题。

1. **用户与任务：** 谁在什么设备上使用，要完成什么；指定一个主要视口。
2. **主角与主动作：** 首屏和关键状态各自最重要的对象/内容是什么、唯一主操作是什么；其他操作如何降级。
3. **品类基线与偏离：** 哪些熟悉结构应沿用以减少学习成本；改变常规模式的产品理由是什么。
4. **方向：** 一句话描述第一眼感受和整页的组织原则。
5. **字体、色彩与主视觉：** 字体角色、底色/强调色用途、主图或图形来源；不确定处标为待验证。
6. **动效与状态：** 主操作反馈、一个关键状态转变，以及相关的空/加载/成功/失败状态。

用户已给定完整方向或品牌规范时，记录并沿用，不重新发散。用户说“你定”“直接做”或任务要求一次交付时，完成方向卡后继续实现，不停在确认点。

如任务需要同类产品参考，观察两三个真实页面，拆出内容排序、骨架、字体、颜色、素材、文案和场景，并记录每个选择“是什么、为什么”。交互参考单独记录“触发 → 对象变化 → 反馈 → 下一状态”，不要从视觉风格臆测操作方式。无法取得真实画面时说明未看图，不写成已验证结论。

区分**品类基线**（熟悉且值得沿用）、**品类套路**（可考虑如何改进的默认版式）和**撞脸**（多个视觉特征像同一参考、只换名字，应避免）。React Bits 是面向 React 的 UI 示例与组件来源，不自动等于产品同类或视觉标杆；可从它借鉴视觉和交互模式，并按目标平台重做。

## 2. 形成具体方向

为方向写一行设计意图，再写下可执行选择。可用这些轴描述产品调性，但不为填表而制造风格：

| 观察轴 | 可见证据 |
| --- | --- |
| 能量：安静 ↔ 喧闹 | 饱和度、对比、元素是否碰撞 |
| 完成度：粗粝 ↔ 精致 | 边缘处理、颗粒、对齐精度 |
| 密度：疏 ↔ 密 | 留白尺度、信息数量、叠层 |
| 分量：轻 ↔ 重 | 字重、色块面积、阴影硬度 |
| 严肃度：活泼 ↔ 庄重 | 圆角、图形语气、动效幅度 |

“高级、精致、克制、冲击力”等词必须翻译成具体画面决定。例如：标题采用高反差字族、色相控制在两种；主视觉占首屏约一半；删掉重复说明和同权重的第二个主按钮。概念可从产品专属对象、真实使用场景、材质与环境、相关文化语法或合理的结构突破中生长；不要为了显得特别而任意添加噪点、撕纸边或 3D。

方向卡至少写：方向名/一句话概念、主角与主动作、首屏骨架、字体、色彩来源、主视觉来源、关键状态/动效、资产与技术依赖。先用灰度块检查构图和层级，再补颜色、材质和细节。灰度状态看不出主角与主动作时，不要指望视觉装饰来救。

### 方向的可执行选择

| 维度 | 要决定什么 |
| --- | --- |
| 视觉锚点 | 从产品内容、真实材质、使用场景或相邻领域取一个具体来源 |
| 构图 | 首屏焦点、内容宽度、对齐方式、分栏/叠放关系和留白节奏 |
| 字体 | 标题、正文、数字与辅助信息的层级和字重；先用项目可用字体 |
| 色彩 | 页面底色、文字、品牌色和强调色的面积比例与用途 |
| 表面 | 边框、阴影、圆角、纹理与卡片策略；只保留有助于分组或操作的表面 |
| 交互 | 主操作的反馈、等待/成功/失败状态和一处值得记住的动效 |

方向不应只换主题色。用户明确要求比较时遵从其数量；没有指定数量时最多做三个有实际差异的候选。所有候选使用同一组产品事实和内容，差异落在构图、排版、主视觉或页面结构。用户已指定风格/品牌时，在该范围内比较；每个方向说明适用性，不拿“保底极简风”凑数。完整比较流程见 [显式方向比较](task-explore.md)。

候选页面可用 [方向比较器](style-explorer.md) 并排查看。文字方案已足以选择时，无需先制作比较页；比较器不生成候选，也不替代逐个检查目标视口。

新页面默认先选方向再实现完整交互。若本轮要求一次做完且无需确认，则在适当范围内自行选择并直接完成。不要把普通设计任务卡在确认流程上。

## 3. 按页面任务安排首屏

- **营销/品牌页：** 可以设计有节奏的开场，但先确定首屏骨架，再写短而可信的文案。明确价值、证据和行动路径。
- **列表、内容浏览、后台和工具：** 让真实内容、筛选或工作区尽早出现。首屏避免空洞口号和重复解释。
- **表单/任务流程：** 让用户知道当前位置、需要提供什么、提交后会发生什么；为校验、提交中、成功和失败状态留位置。
- **单组件：** 围绕组件的关键使用时刻设计；同时考虑默认、悬停、聚焦、按下、禁用和窄屏表现。

## 4. 改造既有界面

先保留一张基线截图或记录现有结构。盘点相关设计变量、共享组件和行为。判断任务属于：

- **视觉改版：** 可纠正历史形成的样式问题，保留品牌和熟悉的交互语义。
- **流程调整：** 优先沿用现有视觉，先确认步骤、反馈和状态怎么改变。
- **新增功能：** 沿用现有设计系统，将新功能接入对应页面和组件。

从源头改共享规则或组件，避免只给一个页面打补丁。没有被要求改变的业务行为保持原样，并在交付时说明相关验证范围。

## 5. 截图还原

记录参考图的逻辑视口，拆出主容器、列宽、间距、字号、行高、色彩、图像比例、对齐和浮层关系。先还原大块结构与明暗/色彩比例，再调字体和细节。按 [布局与视口](layout-and-viewport.md) 检查目标尺寸和关键风险状态；没有参考证据的响应式行为按内容优先级推断。

## 6. 实现与收敛

- 遵循目标平台与项目已有的框架、命名、导航、布局和样式约定，保持改动落在实际产品文件中。
- 用真实文案和数据形状排版，检查长标题、空列表、长标签和窄屏折行。
- 每轮集中改一组相关问题，完成后看真实页面；不要靠连续追加装饰掩盖结构问题。
- 做一次减法：删掉不帮助理解、分组或操作的标签、线、阴影、卡片、徽标与动效。
- 字体、层级、色彩或表面处理拿不准时读 [视觉语言指南](visual-language.md)。
- 截图检查的做法见 [验收清单](review-checklist.md)。需要参考外部视觉组件时见 [React Bits 指南](react-bits.md)，按项目技术栈决定借鉴或集成。
